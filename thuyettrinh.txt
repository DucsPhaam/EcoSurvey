"Vấn đề đặt ra: Các trường học và tổ chức giáo dục hiện nay đều cần thu
thập ý kiến sinh viên về nhận thức môi trường, nhưng thường làm thủ công
bằng form giấy hoặc Google Form — thiếu hệ thống quản lý tập trung,
không có cơ chế khuyến khích tham gia, và không theo dõi được hoạt động
thực tế của sinh viên.

EcoSurvey giải quyết bằng một nền tảng web toàn diện với 4 trụ cột chính:

  1. Survey System: Hệ thống khảo sát trực tuyến với đa dạng loại câu hỏi
     (trắc nghiệm, tự luận, thang đánh giá, có/không), hỗ trợ phân quyền
     đối tượng khảo sát theo vai trò (Student, Staff, All).

  2. Participation Tracking: Module nộp minh chứng hoạt động môi trường —
     sinh viên upload hình ảnh, mô tả hoạt động thực tế, Admin duyệt và
     cấp điểm rèn luyện.

  3. Gamification Engine: Hệ thống Eco-Points, Badges và Leaderboard — mỗi
     lần hoàn thành khảo sát hoặc được duyệt minh chứng đều được cộng điểm,
     khi đạt mốc sẽ tự động nhận huy hiệu.

  4. AI Integration: Tích hợp Gemini AI qua OpenRouter API cho hai tính năng:
     FAQ Chatbot trả lời tự động câu hỏi thường gặp, và Auto-Summarize tóm
     tắt báo cáo hoạt động giúp Admin duyệt nhanh hơn."


┌─────────────────────────────────────────────────────────────────────┐
│  SLIDE 4: TECH STACK — LỰA CHỌN CÔNG NGHỆ & LÝ DO                  │
└─────────────────────────────────────────────────────────────────────┘

"Về lựa chọn công nghệ, nhóm em xin giải thích lý do cho từng thành phần:

── FRONTEND ──────────────────────────────────────────────────────────

  • React.js: Được chọn vì kiến trúc Component-Based, cho phép tái sử dụng
    UI components (FeatureCard, SurveyCard, StepCard...) trên nhiều màn hình.
    Virtual DOM (Document Object Model) đảm bảo hiệu năng khi render 
    danh sách khảo sát lớn.

  • Vite: Build tool thế hệ mới, Hot Module Replacement (HMR) gần như tức
    thì — tăng tốc trải nghiệm lập trình gấp nhiều lần so với Webpack.

  • TailwindCSS: Utility-first CSS framework, cho phép xây dựng giao diện
    responsive nhanh chóng mà không cần viết file CSS riêng, đảm bảo thiết
    kế nhất quán giữa các thành viên.

── BACKEND ───────────────────────────────────────────────────────────

  • Node.js + Express.js: Nhóm chọn kiến trúc RESTful API với Express vì
    hệ sinh thái middleware phong phú (Helmet, CORS, express-rate-limit),
    phù hợp với mô hình I/O-bound của ứng dụng khảo sát (nhiều request
    đọc/ghi nhẹ, ít tính toán nặng).

  • Socket.IO: Cần real-time notification — khi Admin duyệt minh chứng hoặc
    có khảo sát mới, user nhận thông báo tức thì mà không cần F5 lại trang.

── DATABASE ──────────────────────────────────────────────────────────

  • MySQL: Đây là lựa chọn có chủ đích. Hệ thống EcoSurvey đòi hỏi tính
    TOÀN VẸN DỮ LIỆU cao — dữ liệu khảo sát, điểm rèn luyện, minh chứng
    hoạt động đều có quan hệ chặt chẽ và không được phép mất mát hay bất
    nhất quán.

    Database được thiết kế theo chuẩn hóa 3NF với 14 bảng dữ liệu, sử dụng
    Foreign Key Constraints quản lý chặt chẽ các quan hệ giữa các bảng.
    Ví dụ: Một SurveyAnswer PHẢI thuộc về đúng một SurveyResponse, và
    SurveyResponse PHẢI thuộc về một Survey hợp lệ — nếu vi phạm, database
    sẽ từ chối thao tác ngay lập tức.

    ★ NẾU THẦY HỎI: 'Tại sao không dùng NoSQL (MongoDB)?'

    → Trả lời: NoSQL phù hợp với dữ liệu phi cấu trúc, schema linh hoạt,
    scale-out ngang. Nhưng EcoSurvey cần ACID transactions (ví dụ: khi cộng
    điểm cho user, phải đảm bảo cả PointLog VÀ cập nhật trạng thái
    Participation đều thành công hoặc đều rollback). MongoDB không hỗ trợ
    multi-document transactions mạnh mẽ bằng MySQL. Thêm nữa, dữ liệu
    khảo sát có cấu trúc rõ ràng (Survey → Question → Answer), quan hệ
    nhiều tầng, JOIN phức tạp — đây chính là thế mạnh của Relational Database.

  • Sequelize ORM: Giúp định nghĩa Model bằng JavaScript (code-first),
    không cần viết SQL thủ công cho từng bảng. Hỗ trợ sync() đồng bộ schema
    (đã loại bỏ alter: true để ngăn việc tự động sinh trùng lặp các chỉ mục
    UNIQUE/INDEX gây vượt quá hạn ngạch 64 keys của MySQL "Too many keys specified").
    Đồng thời hỗ trợ Migration và Seeder để quản lý phiên bản database trong team.

── THIRD-PARTY SERVICES ──────────────────────────────────────────────

  • Google OAuth 2.0: Single Sign-On cho phép user đăng nhập bằng tài khoản
    Google — tiện lợi trong môi trường học đường (Gmail).

  • Cloudflare Turnstile: CAPTCHA thế hệ mới, bảo vệ form đăng ký/đăng nhập
    khỏi bot spam mà không gây phiền hà cho user (privacy-preserving).

  • Cloudinary: Cloud storage cho file upload — ảnh minh chứng và avatar
    được lưu trữ trên CDN, giảm tải cho server chính.

  • OpenRouter + Gemini AI: Tích hợp AI để trả lời FAQ tự động và tóm tắt
    báo cáo hoạt động — giảm tải công việc cho Admin.

  • ExcelJS & PDFKit: Đọc/ghi file Excel (.xlsx) xử lý Import tài khoản hàng loạt & Export khảo sát; render file PDF (PDFKit + font Roboto tiếng Việt) xuất báo cáo hoạt động."


┌─────────────────────────────────────────────────────────────────────┐
│  SLIDE 5: DATA FLOW DIAGRAM (DFD) — LUỒNG DỮ LIỆU                  │
└─────────────────────────────────────────────────────────────────────┘

"Về luồng dữ liệu tổng quan, hệ thống hoạt động theo 4 luồng chính:

  Luồng 1 — Authentication Flow:
  User gửi thông tin đăng ký/đăng nhập → Backend xác thực qua CAPTCHA →
  Kiểm tra credentials → Tạo cặp Access Token (JWT 15 phút) + Refresh
  Token (Cookie 30 ngày) → Trả về cho Frontend.
  Hoặc: User chọn Đăng nhập Google → Passport.js xử lý OAuth flow →
  Google trả profile → Backend match/tạo user → Redirect kèm token.

  Luồng 2 — Survey Flow:
  Admin tạo Survey (Draft) → Publish → Cron job tự động đóng khi hết hạn.
  Student/Staff mở Survey Board → Chọn khảo sát → Trả lời → Submit →
  Backend lưu SurveyResponse + SurveyAnswers → Cộng Eco-Points → Gửi
  Notification real-time qua Socket.IO.

  Luồng 3 — Participation Flow:
  User nộp minh chứng hoạt động môi trường (mô tả + upload ảnh) →
  AI tự động tóm tắt (ai_summary) → Admin xem và duyệt/từ chối →
  Nếu duyệt: Cộng điểm + gửi thông báo. Nếu từ chối: Gửi lý do.

  Luồng 4 — Gamification Flow:
  Mỗi hành động cộng điểm → PointLog ghi lại → Badge Service kiểm tra
  điều kiện (SURVEY_COUNT, PARTICIPATION_COUNT, TOTAL_POINTS,
  LEADERBOARD_RANK...) → Tự động cấp Badge → Cron job chạy mỗi giờ
  kiểm tra Top 10 Leaderboard Badge."


┌─────────────────────────────────────────────────────────────────────┐
│  SLIDE 6: ERD — SƠ ĐỒ QUAN HỆ THỰC THỂ                             │
└─────────────────────────────────────────────────────────────────────┘

"Database gồm 14 bảng, thiết kế theo chuẩn hóa 3NF. Em xin trình bày
các nhóm quan hệ chính:

  ── Nhóm Authentication (3 bảng) ──────────────────────────────────
  • users: Bảng trung tâm, lưu thông tin cá nhân, role (Student/Staff/Admin),
    status (Pending/Approved/Rejected/Locked/Deactivated), hỗ trợ cả local auth
    (password_hash) và Google OAuth (google_id).
  • refresh_tokens: Lưu SHA-256 hash của refresh token, liên kết user_id,
    có cơ chế revoked flag + expires_at.
  • 1 User → N RefreshTokens (hỗ trợ đăng nhập multi-device).

  ── Nhóm Survey (4 bảng) ─────────────────────────────────────────
  • surveys: Tiêu đề, mô tả, target_role, start_date, end_date, status.
  • questions: Thuộc 1 survey, có type (multiple_choice, text, rating, yes_no).
  • survey_responses: Ghi nhận lượt trả lời của user cho survey.
  • survey_answers: Câu trả lời cụ thể cho từng question trong response.
  • Quan hệ: Survey (1) → (N) Question → (N) SurveyAnswer.
              Survey (1) → (N) SurveyResponse → (N) SurveyAnswer.

  ── Nhóm Participation (2 bảng) ──────────────────────────────────
  • participations: Minh chứng hoạt động (event_name, location, description,
    status, ai_summary, reviewed_by).
  • participation_files: File ảnh đính kèm (Cloudinary URL).
  • 1 Participation → N ParticipationFiles.

  ── Nhóm Gamification (3 bảng) ───────────────────────────────────
  • point_logs: Ghi lại mọi giao dịch điểm (action_type: Survey_Completion,
    Event_Report, Bonus, Deduction). Append-only — không sửa/xóa.
  • badges: Định nghĩa huy hiệu (condition_type + condition_value).
  • user_badges: Bảng trung gian N-N giữa User và Badge.

  ── Nhóm Support (2 bảng) ────────────────────────────────────────
  • notifications: Thông báo real-time cho từng user.
  • faqs: Câu hỏi thường gặp, làm ngữ liệu cho AI Chatbot.

  Tại sao point_logs dùng mô hình Append-only (chỉ INSERT, không UPDATE/DELETE)?
  → Để đảm bảo tính minh bạch và kiểm toán: mọi biến động điểm đều có
  dấu vết, không ai có thể sửa lịch sử điểm, Admin có thể truy vết
  từng giao dịch khi cần."

┌─────────────────────────────────────────────────────────────────────┐
│  SLIDE 8: SECURITY — BẢO MẬT HỆ THỐNG                               │
└─────────────────────────────────────────────────────────────────────┘

"Bảo mật là một trong những trọng tâm đầu tư lớn nhất của dự án. Hệ thống
áp dụng mô hình Defense-in-Depth (bảo vệ nhiều lớp):

  Lớp 1 — Transport Layer:
  • HSTS (2 năm) ép trình duyệt luôn dùng HTTPS.
  • Helmet CSP chặn XSS, clickjacking, plugin injection.

  Lớp 2 — Authentication & Multi-Domain Session:
  • JWT Access Token (15 phút, lưu localStorage) + Refresh Token Cookie (30 ngày, SHA-256 hashed).
  • Khôi phục phiên đăng nhập thông minh bằng Bearer Token từ localStorage 
    ở AuthContext (duy trì trạng thái đăng nhập ổn định khi reload trang 
    ngay cả khi browser chặn Cookie 3rd-party cross-domain giữa Vercel & Railway).
  • Google OAuth 2.0 qua Passport.js tích hợp mã hóa `state` (Base64URL) 
    để điều hướng động chính xác về từng client domain Vercel (multi-domain client support).
  • Cloudflare Turnstile CAPTCHA bảo vệ form đăng ký/đăng nhập.
  • Email Service sử dụng Nodemailer tối ưu tự động cho `service: 'gmail'`, 
    tự động làm sạch App Password (strip spaces) và đồng bộ Header 'From' trùng khớp 
    SMTP_USER để chống bị đưa vào Spam/Junk.

  Lớp 3 — Authorization Layer:
  • Role-Based Access Control (RBAC): Student, Staff, Admin.
  • ProtectedRoute component ở Frontend kiểm tra role trước khi render page.
  • Backend middleware kiểm tra req.user.role cho mỗi API endpoint.

  Lớp 4 — Rate Limiting & DoS Protection:
  • generalLimiter: 300 req/phút mount toàn cục trên Express.
  • loginLimiter: 10 req/phút chống brute-force.
  • aiLimiter: 10 req/phút kiểm soát chi phí AI API.
  • surveySubmitLimiter: 5 req/phút chống spam nộp bài.
  • Pagination cap: Giới hạn limit tối đa 100 bản ghi/request chống
    Memory Exhaustion DoS.

  Lớp 5 — Production Safeguards & DB Integrity:
  • Fail-Fast startup: Server dừng ngay nếu thiếu JWT_SECRET, DB credentials,
    OAuth keys hoặc CAPTCHA secret key ở production.
  • CAPTCHA Fail-Closed: Trả HTTP 500 nếu thiếu TURNSTILE_SECRET_KEY ở
    production thay vì bypass.
  • Loại bỏ `sequelize.sync({ alter: true })` chuyển sang `sequelize.sync()` để bảo vệ DB khỏi lỗi cạn kiệt index key (MySQL max 64 keys limit).
  • Loại bỏ hoàn toàn việc đọc JWT từ URL query string để tránh rò rỉ
    token qua Server Logs, Browser History, và HTTP Referer Header."

┌─────────────────────────────────────────────────────────────────────┐
│  MÀN HÌNH 2: ĐĂNG KÝ & ĐĂNG NHẬP                                    │
└─────────────────────────────────────────────────────────────────────┘

"Hệ thống hỗ trợ 2 phương thức đăng ký/đăng nhập:

  ── Đăng ký bằng Form (Local Auth) ──────────────────────────────
  • Nhập: Họ tên, Username, Email, Mật khẩu, Vai trò (Student/Staff),
    Mã sinh viên/nhân viên, Lớp, Khoa.
  • Cloudflare Turnstile CAPTCHA bắt buộc phải hoàn thành.
  • Sau đăng ký → status = 'Pending' → Admin phải duyệt trước khi
    tài khoản được kích hoạt.
  • Hệ thống gửi email xác thực (Email Verification) qua SMTP.

  ── Đăng nhập bằng Google OAuth ─────────────────────────────────
  • Click 'Sign in with Google' → Chuyển đến Google Consent Screen →
    Chọn tài khoản → Backend tạo user nếu chưa có → Redirect về
    Frontend kèm Access Token.
  • Nếu là user Google mới → redirect đến trang Register để bổ sung
    thông tin (mã SV, lớp, khoa).

  ── Quên mật khẩu ───────────────────────────────────────────────
  • Nhập email → Backend sinh reset token (crypto.randomBytes) →
    Gửi link reset qua email → User click link → Đặt mật khẩu mới.
  • Token có thời hạn, sử dụng 1 lần."

Q1: "Tại sao không dùng MongoDB (NoSQL) thay vì MySQL?"
────────────────────────────────────────────────────────
→ "Dạ thưa thầy, hệ thống EcoSurvey có dữ liệu quan hệ chặt chẽ — một
   Survey chứa nhiều Question, mỗi Question có nhiều Answer, mỗi Answer
   thuộc một Response. Chuỗi quan hệ này cần được ràng buộc bằng Foreign
   Key để đảm bảo toàn vẹn.

   Ngoài ra, khi cộng điểm cho user, hệ thống cần ACID transaction —
   phải đảm bảo cả việc tạo PointLog VÀ cập nhật trạng thái Participation
   đều thành công hoặc đều rollback. MySQL hỗ trợ transaction gốc mạnh mẽ,
   trong khi MongoDB chỉ hỗ trợ multi-document transaction từ bản 4.0 và
   hiệu năng kém hơn đáng kể.

   Cuối cùng, dữ liệu khảo sát có cấu trúc rõ ràng, không cần schema
   linh hoạt — đây chính là thế mạnh của Relational Database."


Q2: "Sequelize ORM có chậm hơn viết raw SQL không?"
────────────────────────────────────────────────────
→ "Dạ đúng là Sequelize có overhead so với raw SQL — mỗi query phải qua
   lớp abstraction để build SQL. Tuy nhiên overhead này rất nhỏ (vài ms)
   và được đánh đổi bằng:
   - Tốc độ phát triển nhanh hơn nhiều (code-first, auto-sync schema).
   - Chống SQL Injection tự động qua parameterized queries.
   - Dễ maintain khi team nhiều người.
   Với những query phức tạp (như tính rank Leaderboard), em vẫn dùng
   sequelize.query() viết raw SQL trực tiếp để tối ưu."


Q3: "Tại sao dùng localStorage cho Access Token mà không dùng Cookie?"
──────────────────────────────────────────────────────────────────────
→ "Access Token cần được gửi trong Authorization Header cho mọi API request.
   Nếu lưu trong Cookie, browser sẽ tự động gửi kèm → dễ bị tấn công CSRF.
   localStorage cho phép Frontend chủ động kiểm soát khi nào gửi token.
   Để giảm thiểu rủi ro XSS, Access Token có thời hạn rất ngắn (15 phút)
   và hệ thống có Helmet CSP chặn inline script injection."


Q4: "Socket.IO có scale được khi có nhiều server không?"
────────────────────────────────────────────────────────
→ "Hiện tại với single server, Socket.IO hoạt động tốt vì lưu danh sách
   socket connections trong memory (Map). Nếu cần scale ra nhiều server,
   em sẽ dùng @socket.io/redis-adapter — Redis pub/sub làm message broker
   giữa các server instances, đảm bảo event được broadcast tới đúng user
   dù họ đang kết nối ở server nào."


Q5: "Nếu AI API (OpenRouter) bị lỗi thì hệ thống xử lý thế nào?"
──────────────────────────────────────────────────────────────────
→ "Hệ thống có cơ chế Graceful Degradation. Trong aiService.js, nếu
   OPENROUTER_API_KEY không được cấu hình hoặc API call thất bại, hệ thống
   tự động fallback sang mock functions — trả về câu trả lời cơ bản bằng
   cách matching keywords từ FAQ database. Tính năng AI bị giảm chất lượng
   nhưng hệ thống KHÔNG bị crash hay từ chối phục vụ."


Q6: "Điểm (Eco-Points) có thể bị gian lận không?"
──────────────────────────────────────────────────
→ "Nhóm em đã áp dụng nhiều biện pháp chống gian lận:
   - surveySubmitLimiter: Giới hạn 5 lần nộp/phút.
   - Backend kiểm tra user đã nộp survey chưa trước khi cho phép submit.
   - Minh chứng hoạt động phải qua Admin duyệt thủ công mới được cộng điểm.
   - point_logs là append-only — không ai sửa/xóa lịch sử điểm được.
   - Tài khoản phải được Admin Approve mới được sử dụng → chống tạo
     nhiều tài khoản fake để farm điểm."


Q7: "Hệ thống xử lý user đăng nhập trên nhiều thiết bị thế nào?"
────────────────────────────────────────────────────────────────
→ "Hệ thống hỗ trợ multi-device login. Mỗi lần đăng nhập tạo một
   Refresh Token mới, KHÔNG revoke token cũ. Mỗi thiết bị có cookie
   refreshToken riêng, tất cả đều hợp lệ song song. Nếu muốn chuyển
   sang single-device, chỉ cần revoke tất cả token cũ khi tạo token mới."


Q8: "Tại sao user đăng ký phải chờ Admin duyệt? Có phiền không?"
────────────────────────────────────────────────────────────────
→ "Đây là thiết kế có chủ đích cho môi trường giáo dục. Hệ thống cần
   đảm bảo chỉ sinh viên và nhân viên thật của trường mới được tham gia.
   Admin xác minh Mã sinh viên / Mã nhân viên trước khi Approve. Điều này
   ngăn chặn người ngoài tạo tài khoản giả để ảnh hưởng kết quả khảo sát.
   Ngoài ra, Email Verification cũng giúp xác nhận email hợp lệ."


Q9: "Hệ thống có hỗ trợ export dữ liệu không?"
──────────────────────────────────────────────
→ "Có ạ. Backend có module exportRoutes.js cho phép Admin export kết quả
   khảo sát. Hiện tại hỗ trợ export qua API, tương lai sẽ mở rộng thêm
   định dạng Excel và PDF."


Q10: "Cron job nếu bị lỗi thì sao? Có log không?"
──────────────────────────────────────────────────
→ "Cron job được bọc trong try/catch. Nếu lỗi, logger.error ghi lại
   chi tiết lỗi vào Winston log (console + file). Cron chạy mỗi giờ
   nên nếu 1 lần lỗi, lần chạy sau sẽ bắt lại các survey chưa được
   close. Không ảnh hưởng đến hoạt động chính của server."
